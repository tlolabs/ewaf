# EWAF development rules

- This repository uses a nonblocking development and CI/CD model. Tests, builds and security checks report diagnostics; none are required status checks or prerequisites for commits, pushes, merges or unrelated work. Do not add required reviews, manual release approvals or blocking status checks without explicit owner authorization.
- The owner's CI policy, updated 2026-11-08, is one scheduled check on Sunday morning Pacific time. Build only newly tagged version releases on native Linux and Windows x64 and ARM64 runners, with basic compilation, core and window smoke checks. Do not run CI on pushes, pull requests, or tag creation. Do not run macOS CI or full regression suites in the weekly workflow.
- Owner update 2026-11-12: weekly Linux/Windows CI now packages tagged releases, performs basic final-package startup/integrity/dependency smoke checks, and uploads successful target assets to the matching already-published release. It must not create releases, change Latest, publish authenticated updates, or run macOS builds. Only the isolated publisher receives contents:write; build jobs remain read-only. Legacy workflows retained for reference must remain disabled unless the owner changes this policy. For separately authorized publication, release only platform artifacts that passed integrity and functional checks; failures on other platforms must not block them. Failed artifacts are never published. Stable and beta/RC releases retain their version-matching tag conventions. Existing release assets are checked byte for byte and never overwritten.
- Local distributable macOS packages are Developer ID signed and notarized by default; explicit dev/test packages may remain unsigned. Direct downloads are not authenticated automatic updates. Preserve signed update-manifest, Sparkle and Windows Authenticode verification exactly; never add unsigned packages to the updater feed or weaken runtime security.
- Do not automatically retry previously attempted releases. Keep failures visible in the workflow results. Record implementation separately from platform evidence; never claim a skipped or untested platform passed. A weekly smoke pass does not qualify an installer or authenticated update.
- Read docs/BEHAVIOR.md and docs/PARITY.md before changing a workflow. Rust in crates/ewaf-core is authoritative for platform-independent behavior. Do not reproduce date, naming, filtering, confirmation, conflict or recovery rules in Swift or C++ presentation code.
- Preserve native SwiftUI/AppKit for production macOS. Windows, Linux and the internal-only macOS ARM64 reference use one shared Qt presentation in platform/qt. Keep OS adapters below that presentation. The reference must never enter production releases or updates. Presentation owns controls, accessibility, dialogs, lifecycle, scheduling and preferences storage.
- Every intentional user-facing change must explicitly evaluate all three platforms, implement native equivalents, update the parity matrix and add meaningful regression coverage. Document implementation versus verified status. Ask the owner before a significant behavioral compromise or compatibility break.
- Preserve com.tlolabs.ewaf, defaultWeekday, rangeStart, rangeEnd, rangeWeekday, Codable dates and generated directory contents. The owner authorized legacy removal on 2026-09-16; the references live on codex/archive-legacy-1.0.2. The owner also authorized removal of all Python-derived fixture data; keep legacy code and data out of the active tree.
- Run ./script/build_core.sh before swift test. Rust archive changes must update the generated C build-stamp header so SwiftPM/Xcode relink. Never commit generated binaries, build-stamp headers or credentials.
- For development changes, run cargo fmt/clippy/tests with the locked toolchain, applicable native tests, version checks and package validation. These local development checks do not expand weekly CI beyond basic smoke checks. A failed Windows or Linux job is a regression even if macOS passes.
- Cargo.toml owns the application version. Update/check native copies and regenerate dependency notices/locks when dependencies change. Stable tag versions must match Cargo.toml. Publish only successful, verified platform artifacts from that tag; a platform failure must not block other platforms.
- Use script/build_and_run.sh for macOS build/run and the platform scripts for packaging. Development artifacts must work without signing credentials via explicit --unsigned packaging; distributable macOS packaging requires SIGNING_IDENTITY and NOTARY_PROFILE from secure local configuration.
- Create unsigned Git commits (`commit.gpgsign=false`; do not use `-S` / `--gpg-sign`). Preserve DCO `Signed-off-by` trailers as a convention. Release tags need no signature or owner-only trigger; they must match Cargo.toml. Platform trust is described in CODE_SIGNING_POLICY.md.

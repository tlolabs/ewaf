# Authenticated desktop updates

## Decision and scope

EWAF now has an application-independent Rust component, `crates/tlo-updater`, and a thin `ewaf-update` executable. Neither depends on EWAF Core or AVID Core. The library has its own version; application binaries continue to inherit Cargo's workspace version. This change implements EWAF only. Other repositories were inspected read-only at the owner's direction.

Use GitHub Release assets, not HTML scraping or unauthenticated API polling. Windows and Linux fetch `https://github.com/tlolabs/ewaf/releases/latest/download/update-manifest.json`; GitHub's latest stable release excludes drafts and prereleases. Independently authenticated metadata must also declare stable, non-draft, a strict stable SemVer, the pinned repository and application ID. The manifest is bounded to 1 MiB, artifacts to 2 GiB. Redirects stay on HTTPS GitHub release storage. No credentials, cookies, machine identifiers, user data or analytics are sent. GitHub still receives ordinary network requests, including the client's IP address.

The native layers own controls, preference storage, scheduling and consent. Rust owns Windows/Linux discovery, SemVer, compatibility, signature verification, checksums, bounded downloads, and scheduling policy. Defaults: check after 24 hours since a successful authenticated check; failed attempts back off one hour; native timers revisit eligibility hourly. Manual checks bypass the interval. A backwards clock jump does not permanently disable checks. An outage leaves the app usable and never authorizes an installation. Downloads are not resumed across attempts; incomplete temporary files are deleted.

### Installation choices

- **macOS: Sparkle 2.9.6**, pinned in SwiftPM and by the release-tool archive digest. Its native interface, scheduler, download verification, installation helper and relaunch behavior are retained. Feed and archive Ed25519 signatures are mandatory; verification happens before extraction. Signed-feed failure fallback is disabled with `SUSignedFeedFailureExpirationInterval=0`. No unattended installation or system profiling. Production archives additionally require Developer ID, hardened runtime, notarization, stapling, expected Apple team, bundle identity, version and architecture. Sparkle checks its archive signature; SHA-256 is checked by release qualification, not a second macOS downloader. This is an intentional, documented use of the established component rather than replacing its security-sensitive installer. Separate architecture feeds prevent an ARM application being replaced by an Intel artifact. Active creation in any window blocks termination/relaunch. Existing scene/preferences handling preserves working ranges.
- **Windows: native Windows Installer transactions**, packaged using pinned WiX 4.0.6. A background helper authenticates the manifest and download. The native dialog coordinates closing all windows. The native `ewaf-installer` helper then requires a valid Authenticode chain, the exact pinned publisher, fixed MSI UpgradeCode, product name, manufacturer, version and architecture. It keeps a read-only handle open to prevent package modification/replacement through installation. A READY/COMMIT handshake ensures verification succeeds before EWAF closes; if active work starts during verification, the UI aborts. The self-contained helper runs from staging, outside the installation directory, without changing PowerShell policy. It waits for normal exit, never kills a process, disables Restart Manager termination and suppresses reboot. Windows Installer provides failure rollback. The user reopens EWAF using its shortcut. Registry preferences and generated folders are outside the installer payload. The old ZIP remains useful for development; its in-place install script is not used for automatic updates. Existing portable installs migrate once to the MSI's per-user `LocalAppData/TLO Labs/EWAF` directory. Their original folder is not deleted.
- **Linux: full authenticated AppImage download and same-directory atomic replacement**, retaining a synced executable backup. The old image must be a regular type-2 AppImage; its directory must not be shared-writable or reached through symlinks. The helper holds a stable per-target transaction lock, checks the old image has not changed, verifies staged bytes and ELF architecture, and writes a durable monotonic version/digest journal before atomic replacement. An old still-running instance cannot replace a newer installed/prepared version. A crash after journal persistence allows a retry of the exact same version and digest. Keep the hidden `.tlo-update.json` and `.tlo-update.lock` files beside the AppImage; removing the journal discards rollback history. It retains and syncs the prior executable backup. It never executes an incoming image for inspection and never terminates or relaunches the current application. Shared preferences store policy and timestamps; Linux imports prior dconf values into its JSON store. `.deb` installations offer a clear package-manager/manual AppImage migration path. Production AppImages are bound to the independently signed Ed25519 release manifest by exact digest and size. GitHub build attestations add provenance. There is no separate AppImage signing-key requirement.

[AppImageUpdate](https://github.com/AppImageCommunity/AppImageUpdate) was evaluated: it offers mature delta reconstruction but also owns feed selection and replacement, which would create a second selection path outside the exact authenticated release candidate. EWAF uses a small full-file transaction to retain a single trust decision; bandwidth-saving deltas are deferred. [Velopack](https://docs.velopack.io/packaging/operating-systems/windows) was evaluated: its directory replacement can terminate processes holding `current`. The MSI adapter delegates transactions to Windows and explicitly disables forced closure. Neither choice removes the need for native older-to-newer qualification.

## Wire contract and trust chain

See `updates/manifest.schema.json`. `update-manifest.json` is a JSON envelope with `key_id`, base64 `payload` and base64 `signature`. Sign the exact decoded UTF-8 payload bytes using Ed25519; do not parse and reserialize before verification. The installed executable embeds `updates/trust.json`. A key supplied by the network is never accepted. Verify the signature before parsing the payload.

Payload schema 1 contains application ID, repository, version, exact `vMAJOR.MINOR.PATCH` tag, stable channel, draft flag, RFC3339 release metadata timestamp, expiry, canonical release notes URL, restart/migration information (a non-null migration blocks the shared automatic installation path and directs the user to manual instructions), and one artifact per supported target. Each artifact contains platform, architecture (`x64` or `arm64`), minimum OS, package format, deterministic filename, exact tag-bound GitHub asset URL, byte size, lowercase SHA-256, native signer identity and, on macOS, a Sparkle archive signature. Linux minimum OS denotes the minimum glibc version (`2.39`), not a distribution marketing version. Windows uses the OS build version; macOS uses the product OS version.

The canonical production filenames are:

- `ewaf-<version>-macos-<arch>.zip`
- `ewaf-<version>-windows-<arch>.msi`
- `ewaf-<version>-linux-<arch>.AppImage`

The six-artifact manifest is generated only from platform verification receipts bound to the final artifact digest and source commit. Receipts are CI inputs, not client trust anchors. Their provenance is the same-commit native workflow; the final manifest signature authenticates the resulting metadata. All six target jobs and final verification must pass before draft upload. There is no partial-platform stable update publication in this implementation.

`appcast-arm64.xml` and `appcast-x64.xml` are generated from that same release data and signed with Sparkle's official `sign_update`. Sparkle's `CFBundleVersion` and short version both equal the Cargo SemVer; CI counters are no longer updater versions. An owner-created annotated tag must match Cargo and the native package metadata. `SHA256SUMS`, the dependency inventory, notices, a CycloneDX source-dependency SBOM, signatures, and attestations accompany the release. The SBOM describes locked dependencies across the release family; it does not replace platform-specific binary/vendor dependency audits. Unsigned checksums alone never authorize installation.

Trust chain: installed app/package → pinned application-specific Ed25519 key → signed metadata → exact artifact digest/length/version/target → native installation adapter. macOS additionally uses Sparkle's signed archive and Apple identity; Windows additionally verifies Authenticode and the MSI identity at install time. GitHub, a CDN, or a corrupted download cannot substitute a package without the private manifest/archive signing key. A compromised signing key or a same-user attacker controlling the running application is outside that guarantee. Comparing against the installed version prevents downgrade and same-version installation; expiry bounds stale signed metadata replay but cannot prove that GitHub has not withheld a newer release. OS clock correctness is assumed.

The shared Windows/Linux manifest expires after at most 90 days. Sparkle uses its independently signed appcast and installed-version checks; it does not apply this JSON expiry. An expired channel fails closed with manual fallback; it does not reinstall an old update. The owner must publish a new qualified stable release before expiry if uninterrupted automated discovery is required. There is no background service or scheduled paid channel refresh.

## Enrollment, ownership and rotation

Thomas Lothian remains the sole owner and release/signing approver. Public trust is deliberately empty until owner-controlled enrollment; no production private key was generated, read or committed by this change. Development builds do not perform production update checks. `EWAF_UPDATE_CHANNEL=stable` is a build-time channel gate, not a runtime override. Production release validation refuses empty trust or missing required Apple/Windows identity or update-manifest signing.

Enroll an **EWAF-specific** Sparkle Ed25519 seed using the pinned `generate_keys` tool and keep it in Keychain and an offline recovery backup. Export only into the protected production secret `TLO_UPDATE_SIGNING_SEED` when setting up CI; it is the base64 32-byte seed accepted by both Sparkle and ring. Commit its public key under a descriptive ID in `updates/trust.json`, together with the Apple team ID and exact Azure signing certificate subject. Do not reuse another application's key merely because it exists. The first key is Sparkle's active key; the release seed must match it. Restrict environment/secret access and review tag-triggering permissions.

Other required existing infrastructure: Developer ID certificate/Keychain or protected CI import, Apple notarization credentials, the project's Azure Artifact Signing account and OIDC identity. This change creates no account or paid subscription. Missing Azure credentials do not permit PFX or unsigned production fallback. The documented Windows distribution approval must also be resolved by the owner; `WINDOWS_DISTRIBUTION_APPROVED=true` records that external resolution, not a new license judgment by the updater.

For routine native certificate renewal, retain the Apple team and Windows publisher identity. Test both old and new artifacts. A changed identity requires a bridge released under the currently trusted identity. For manifest-key rotation, keep old keys and the existing feed available, ship an old-key-signed bridge that adds the new public key, and qualify the complete old → bridge → new sequence before retiring a key. The Rust verifier supports multiple enrolled keys; the current single-key Sparkle feed does **not** implement automatic multi-key feed routing. That routing/bridge is required before changing Sparkle's active key. Do not just replace the first public key and latest appcast. If an old key is lost or compromised, stop channel publication, revoke access, publish an incident notice and distribute a manually authenticated replacement; never disable signature checks as recovery.

## Release procedure

1. Update Cargo and native version copies together; run `script/check_versions.py`. A stable tag names exactly this commit/version. Protect the `production` environment and signing secrets. Run production trust preflight before signing.
2. Run the complete native matrix. Normal development tests need no signing credentials. Native Windows builds now produce a test MSI; Linux builds produce an AppImage using checksum-pinned `linuxdeploy`, `appimagetool` and runtime inputs. Tool pins may reference upstream continuous build tools, but a moved upstream asset fails its pinned digest. Application update candidates can never use a continuous tag.
3. Sign Windows-owned executables with the configured Azure account, then build/sign MSI; verify using `ewaf-installer --verify-only` and emit a receipt. Build AppImages from the same commit, verify architecture/version and the embedded helper, emit a digest-bound receipt, and attest the package. Keep the remaining platform credentials isolated.
4. After all required jobs, sign nested Sparkle code and the macOS bundle, notarize, staple, assess Gatekeeper, and emit final macOS receipts. `script/build_update_release.py` requires all six final artifacts/receipts from this commit, signs the manifest and appcasts, and authenticates every local artifact. No private key is written by that script; Sparkle receives it on stdin.
5. Upload a draft with attestations. The workflow refuses to modify an already-published release or clobber assets. Owner publication is separate. Never publish a draft merely because compilation passed; all platform installation qualification evidence below is required for an updater-qualified release.
6. Publication triggers `update-qualification.yml`: inspect actual stable release flags, discover using the shared client, authenticate/download every actual asset, and verify GitHub attestations. This checks the network channel, **not installation**.

`cargo run --locked -p tlo-updater --bin tlo-release -- verify updates/trust.json <directory>/update-manifest.json` verifies a local release. `... -- published updates/trust.json <older-version>` verifies real GitHub discovery/authentication/download without installation or mutation.

## Troubleshooting

“Not configured” / “development build”: expected until trust enrollment and a stable build. “Invalid signature” / “unknown key”: stop; check enrollment and the protected signer, do not retry using a checksum-only package. “Expired manifest”: use the official manual release path while the owner renews the release. “No compatible update”: current version, minimum OS or platform may already be the best supported choice. Network/rate/timeout failures leave folder creation available; failed checks back off.

Linux permission/path errors: move the AppImage to a private writable directory or use the package manager. Keep `ewaf-previous-*.AppImage` until the new version works; restore it manually after closing the application if necessary. Windows errors are displayed by the native installer adapter; a failed MSI transaction rolls back rather than deleting user files. Close all independently launched EWAF instances and retry. macOS issues use Sparkle's standard UI and unified logging. Never bypass Gatekeeper, Authenticode, signed-feed verification or manifest checks.

## Adoption and neighboring-repository audit

The initial audit found ATIV's app-specific Rust helper (`crates/ativ-update`), a signed `latest.json` envelope, stable/development feeds, Sparkle preparation and a portable Windows helper. Its old payload has no explicit application ID, and its wire shape differs from this contract. Do not delete that feed/helper until a bridge is proven. Migrate discovery/authentication to the canonical shared library, preserve old signatures/feed assets during transition, keep native media-work guards, and separately assess its portable installation adapter.

EnCAP has an Objective-C Sparkle bridge and existing public/private-key file **paths** (private contents were not opened), plus native signing workflows and AppImage packaging. During this session its working tree also gained an independently developed `updater/` crate named `tlo-updater` and `encap-update` wrapper. That prototype has a different manifest (`assets` map, target aliases, single public key, different migration fields), and its files were changing concurrently. It is **not wire-compatible** with this implementation. Neither uncommitted working tree should become another application's production dependency.

Before organization-wide adoption, reconcile these two prototypes into one separately versioned TLO Labs updater repository/package, choose a single versioned contract, port the union of negative tests, and pin an immutable revision from each application. The present repository-local library is an extraction candidate, not a claim that this reconciliation has happened. This temporary duplication is explicitly recorded because reusing an actively changing sibling path would make builds non-reproducible and could silently break installed clients. ATIV/EnCAP were not changed in this task, per owner scope. AVID Core is not an updater dependency.

For a new adopter: supply its own application ID, repository, public keys/native identities and authoritative version; depend on the reconciled library by exact revision; add its thin helper plus native scheduling/UI/install adapter; generate manifests using the common release tooling; retain its old channel until bridge qualification passes. Do not copy the download or version code into another app. Library publication, sibling migration and organization-wide standardization remain separate work.

## Internal Avalonia Mac reference

The internal-only ARM64 reference has a distinct identity and storage, no update helper/Sparkle payload, a compiled internal flag and a runtime macOS guard before any shared updater invocation. The production Mac updater remains in the native SwiftUI app. CI artifact naming, production collection filters and release assembly rejection prevent the internal reference from entering a production update. This structural isolation does not replace signed older-to-newer production qualification.
